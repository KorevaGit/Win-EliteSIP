# Закрытие клиента и пропавшие вызовы: добавочный 724

Обновление v38: ошибки записи SQLite больше не скрываются от диагностики. В основной журнал передаются тип операции, основной/расширенный код SQLite и счётчик отказов без параметров SQL и номеров. Архив содержит history-status.txt с исходом открытия, числом ошибок и временем последней ошибки. OpenOutcome по-прежнему описывает только открытие базы; для последующих ошибок есть LastWriteFailure/WriteFailureCount. Ошибка внешнего приёмника диагностики не завершает поток истории. Автоматический повтор потерянной записи и аварийная сохранность очереди ещё не реализованы; находки по истории остаются открытыми.

Дата: 13.11.2026. Ветка ui; исходная точка аудита e66331e. Старый архив сотрудника пуст, время сбоя и версия клиента неизвестны. Ниже — воспроизведённые механизмы отказа, а не установленная причина конкретного инцидента.

## Результат

Стук может нарушить доступность регистрации, но сам по себе не объясняет завершение процесса. Найдены отдельные кандидаты для аварийного закрытия и отсутствующей истории. Их исправление в аудиодвижке и хранилище ещё требуется; данная сборка меняет расписание стука и сбор свидетельств, а не устраняет все найденные отказы.

### Аудиопоток может завершить весь процесс — P1

`WasapiVoiceAudioEngine.StartThread` запускает тело рабочего потока без общей границы обработки исключений. В CaptureLoop/RenderLoop получение COM-интерфейсов находится до локального try; отдельные участки FeedLoop также не защищены общей границей. DispatcherUnhandledException защищает UI, но не эти потоки. AppDomain.UnhandledException записывает ошибку, не предотвращая завершение.

В отдельном дочернем процессе через существующий StartThread введён COMException с HRESULT 0x88890004. Получены IsTerminating=True и код выхода 0xE0434352. Это проверка поведения при исключении, а не воспроизведение реального отказа гарнитуры сотрудника.

Дополнительный риск: Teardown после тайм-аута JoinThread в одну секунду продолжает освобождать COM-клиенты, устройства и события. Незавершённый поток может обратиться к уже освобождённому ресурсу. Этот сценарий подтверждён чтением кода, зависание физического драйвера не воспроизводилось.

Следующий шаг: защитить полные границы рабочих потоков, записывать стек/HRESULT, передавать восстановимые отказы устройства супервизору и согласовать завершение потоков с освобождением ресурсов.

### Ошибка записи истории скрывается — P1

`CallHistoryStore.TryExecute` подавляет SqliteException, возвращая 0. Begin/MarkAnswered/Finish работают через очередь и не сообщают об ошибке вызывающему коду. OpenOutcome после ошибки записи остаётся Ready.

На временной базе PRAGMA query_only=ON воспроизведено: все три метода вернулись, строк нет, состояние Ready. После снятия ограничения контрольный вызов сохранился. Это не доказывает, что у 724 база была read-only: возможные диск/права/блокировки требуют его журнала.

Следующий шаг: журналировать ошибки SQLite с кодами, сообщать о состоянии записи и предусмотреть восстановление после временных отказов.

### Очередь истории оставляет окно потери при аварии — P2

Begin и MarkAnswered возвращаются до фиксации на диске. При искусственно задержанной очереди после возврата обоих методов независимое соединение видит 0 строк; после Flush — 1. Аварийное завершение до фиксации может оставить звонок без записи. Восстановление незавершённых звонков при старте помогает только уже существующим строкам. Между SIP-ответом и сохранением MarkAnswered также есть окно неверного результата вызова.

Контрольная нагрузка: 1000 принятых вызовов подряд, сохранено 1000 (около 4,35 с). Сама частота звонков потерю не воспроизвела. Стенд не моделирует реальную гарнитуру, RTP и сеть сотрудника.

## Изменения стука

- Значение по умолчанию — 3600 секунд. При обновлении старое штатное значение 600 заменяется на 3600 один раз (ревизия настроек 3); нестандартные значения сохраняются.
- Неудачная регистрация и принудительное восстановление регистрации обходят часовое ограничение. Новый агент после смены сети/переподключения выполняет первый стук без ожидания часа. Существующая отсрочка полного переподключения до окончания активного разговора сохранена.
- Параллельные последовательности одного PortKnocker выполняются по очереди; их пакеты больше не перемешиваются. Повторный loopback-опыт подтвердил порядок: все 4 пакета первой попытки, затем все 4 второй. Это исправляет NET-3 исходного аудита.
- Реальный TTL допуска на шлюзе неизвестен. Час задан по пожеланию пользователя, соответствие правилу маршрутизатора не проверено.

Остальные сетевые находки исходного аудита сохраняются: дедлайн снятия регистрации не ограничивает транзакцию, DNS не перебирает адреса, ожидание ICMP-эха увеличивает интервал пакетов. Периодический стук ожидается в keepalive-цикле и может задержать его следующую отправку; это не означает остановку всех SIP-пакетов.

## Свидетельства для техподдержки

С версии v36 архив собирает настоящие файлы журналов и crash.log, включая старое расположение. В v37 добавлен windows-crashes.txt: события Application 1000, 1001, 1026 с упоминанием исполняемого файла клиента за последние 30 суток, до 2000 просмотренных событий. При отсутствии событий или доступа файл объясняет результат. Содержимое проходит редактирование секретов.

Сбор выполняется в фоне. Настройки WER и системного реестра не меняются, дампы памяти не включаются. Поэтому файл может дать свидетельства старой аварии, но наличие события не гарантируется. API: [EventLogReader.ReadEvent](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.eventing.reader.eventlogreader.readevent?view=windowsdesktop-10.0).

Интеграционная проверка архива подтвердила summary.txt, environment.txt, windows-crashes.txt, elitesip.log, collection.txt и удаление контрольного пароля.
