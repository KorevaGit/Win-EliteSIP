# Выпуск и выкладка обновлений

Заведено 25 сентября 2026 вместе с выпуском 0.1.56, когда линия выпусков
переехала из Cloudflare R2 на собственный сервер компании.

## Каналы

| | Старый (по 0.1.55) | Новый (с 0.1.56) |
|---|---|---|
| Адрес | `https://get.elitesip.vip` | `https://update.elitesip.vip:8081` |
| Что за ним | бакет R2 `elitesip-updates` за Worker'ом | свой сервер, HTTPS на 8081 |
| Как выкладывать | S3 API R2 | закрытый объектный API (`PUT /internal/objects/<ключ>`, Bearer) |
| Что отдаёт клиентам | `releases/`, а также `activations/`, `presets/`, `access/`, `revoked/` | только `releases/` |

Пути и авторизация выпусков у обоих одинаковые: `GET/HEAD releases/current.json`
(подписанный манифест, кэш 5 минут) и `GET/HEAD releases/EliteSIP-<версия>.exe`
(поддерживает `Range`, кэш неизменяемый — файл после выкладки не
переписывается). Обе ссылки под HTTP Basic, realm `restricted`, пара та же,
что вшита в клиент. Без пары — 401.

## Почему у клиента теперь два адреса

До 0.1.56 заводская настройка (`provisioning.json`) держала один адрес
`updates.baseURL`, и от него строилось всё: манифест выпуска, пакет активации,
предустановки, помашинный доступ и отзыв. Новый сервер отдаёт только
`releases/`. Заменить `baseURL` целиком значило бы увести туда и линию панели —
а она молчит при ошибке по построению, и узнали бы об этом только на чистой
машине (ровно так прошло 10 сентября 2026).

Поэтому с 0.1.56 у канала появился необязательный `updates.releasesURL`:

```json
{
  "updates": {
    "baseURL": "https://get.elitesip.vip",
    "releasesURL": "https://update.elitesip.vip:8081",
    "user": "…",
    "password": "…"
  },
  "presetsPublicKey": "…",
  "releasesPublicKey": "…"
}
```

`releasesURL` не задан — выпуски там же, где панель. Понимают его и
приложение, и обновляльщик (`tools/Updater`), который ходит в канал сам от
SYSTEM. Когда панель переедет на новый сервер, достаточно поменять `baseURL`.

## Почему 0.1.56 переходный

Установленные машины (≤ 0.1.55) читают старый канал и узнают о новом адресе,
только поставив выпуск, в котором он записан. Поэтому 0.1.56 выкладывается
**на оба канала**, строго в таком порядке:

1. **Новый сервер.** Установщик, затем манифест с
   `url = https://update.elitesip.vip:8081/releases/EliteSIP-0.1.56.exe`.
   Проверка: манифест отдаётся (200), совпадает с подписанным, установщик
   скачивается, sha256 и размер сходятся, без пары — 401.
2. **Только после этого — старый R2.** Тот же установщик байт в байт и второй
   манифест, подписанный тем же ключом, но с `url` на `get.elitesip.vip`.
   Старые машины обновятся до 0.1.56 оттуда же, откуда взяли манифест.
3. **Дальше — только новый сервер.** 0.1.56 и новее в старый канал за
   выпусками не ходят.

Почему не отправить старые машины качать с нового сервера: клиент ≤ 0.1.55
шлёт пару Basic на любой хост из `url`, и полагаться на то, что с чужим хостом
всё сложится, нельзя. С 0.1.56 это правило записано в коде:
`ReleaseManifest.IsServedFrom` — установщик качается только с того же хоста
(схема, имя, порт), что и манифест, иначе отказ и строка в журнале.

Та же проверка закрывает ловушку переезда: выпуски по 0.1.55 перенесены на
новый сервер вместе с манифестом, а `url` в нём подписан и смотрит на старый
хост. Такой манифест 0.1.56 просто не касается (версия не новее), а если бы
касался — клиент отказался бы качать, а не повёз пару на `get.elitesip.vip`.

Порядок 1 → 2 обязателен: наоборот старые машины обновились бы до 0.1.56 и
пошли на новый сервер раньше, чем там появился манифест, — и остались бы без
обновлений.

## Как выпускать (с 0.1.57 и дальше)

Один раз на машине сборки, вне репозитория, в `%APPDATA%\EliteSIP-release\`:

- `provisioning.json` — заводская настройка выпуска (см. выше);
- `publish.local.json` — доступы к каналам:

```json
{
  "update": {
    "baseURL": "https://update.elitesip.vip:8081",
    "basicAuth": "elitesip:…",
    "adminToken": "…"
  },
  "legacy": {
    "baseURL": "https://get.elitesip.vip",
    "basicAuth": "elitesip:…",
    "r2": { "accountId": "…", "bucket": "elitesip-updates", "accessKeyId": "…", "secretAccessKey": "…" }
  }
}
```

`adminToken` берётся у владельца сервера — переменная CI `ELITESIP_ADMIN_TOKEN`
в GitLab-проекте `elitesip_update`. В Git ему нельзя. Раздел `legacy` после
0.1.56 не нужен.

Дальше:

```powershell
.\tools\release.ps1 -Version 0.1.57 -SigningKey C:\keys\releases.key -CertificateThumbprint …
.\tools\publish.ps1 -Channel update -Version 0.1.57
```

`release.ps1` собирает, прогоняет проверки, кладёт заводскую настройку в
публикацию (и отказывается, если её канал выпусков не совпадает с `-BaseUrl`),
собирает установщик, считает sha256 и подписывает манифест, после чего читает
его кодом клиента. `publish.ps1` сверяет манифест с установщиком ещё до сети
(версия, `url` на этом же канале, sha256, размер), кладёт сперва установщик,
потом манифест, и проверяет канал с парой Basic.

`publish.ps1 -VerifyOnly` — проверить, что канал отдаёт сейчас, ничего не
трогая.

Переходный выпуск собирался так:

```powershell
.\tools\release.ps1 -Version 0.1.56 -SigningKey … -LegacyBaseUrl https://get.elitesip.vip
.\tools\publish.ps1 -Channel update -Version 0.1.56
.\tools\publish.ps1 -Channel legacy -Version 0.1.56   # только после успеха предыдущей
```

## После выкладки

Поставить выпуск на одну машину и убедиться, что она обновилась сама.
Проверка «манифест разобрался» этого не заменяет: установщик запускает
Windows, а не мы.
