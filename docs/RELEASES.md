# Выпуск и выкладка обновлений

Заведено 25 сентября 2026 вместе с выпуском 0.1.56, когда канал переехал из
Cloudflare R2 на собственный сервер компании.

## Каналы

| | Старый (по 0.1.55) | Новый (с 0.1.56) |
|---|---|---|
| Адрес | `https://get.elitesip.vip` | `https://update.elitesip.vip:8081` |
| Что за ним | бакет R2 `elitesip-updates` за Worker'ом | свой сервер, HTTPS на 8081 |
| Кто пишет | панель EliteSupport (её больше нет) | корпоративный сайт Spark, раздел EliteSIP |
| Состояние | **заморожен**: новых ключей, предустановок и отзывов там не будет | действующий |
| Как выкладывать выпуск | S3 API R2 | закрытый объектный API (`PUT /internal/objects/<ключ>`, Bearer) |

Новый сервер отдаёт весь контракт канала, с теми же путями, форматами и
подписями, что были в R2:

- `releases/current.json` и `releases/EliteSIP-<версия>.exe` — выпуски. Манифест
  кэшируется 5 минут, установщик — неизменяемый (поддерживает `Range`);
- `activations/<адрес>` — пакет активации: общая пара Basic, однократно, 48 часов;
- `presets/current.json` — предустановки;
- `access/<id>`, `revoked/<id>` — помашинные объекты, ключ машины, realm `machine`.
  404 на `revoked/<id>` — это «не отозвана», а не ошибка.

Всё из R2, включая `machines/`, `access/` и `revoked/` уже активированных
машин, туда перенесено. Пара Basic та же, что вшита в клиент; без неё — 401.

## Что меняется в клиенте

В заводской настройке 0.1.56 `updates.baseURL = https://update.elitesip.vip:8081`,
и оттуда клиент берёт всё: выпуски, активацию, предустановки, доступ и отзыв.
То же читает обновляльщик (`tools/Updater`), который ходит в канал сам от
SYSTEM.

Повторная активация после обновления не нужна: идентификатор машины и её ключ
лежат в `settings.json` (ключ под DPAPI с постоянной солью), общая пара — в
`provisioning.json` рядом с программой. Ни то ни другое к хосту не привязано,
Credential Manager и кэш WinHTTP не используются. Установщик заменяет
`provisioning.json`, настройки пользователя остаются.

Клиент понимает и необязательное `updates.releasesURL` (отдельный корень для
выпусков). В заводской настройке его быть не должно: `release.ps1` откажется
собирать с ним.

С 0.1.56 установщик качается только с того же хоста (схема, имя, порт), что и
манифест: `ReleaseManifest.IsServedFrom`. Пара Basic едет вместе с запросом, и
на чужой хост её не отправят. Это закрывает ловушку переезда: выпуски по 0.1.55
перенесены на новый сервер вместе с манифестом, а `url` в нём подписан и
смотрит на старый хост.

## Почему 0.1.56 переходный

Машины на 0.1.55 и раньше читают замороженный R2 и узнают о новом сервере,
только поставив выпуск, в котором он записан. Поэтому 0.1.56 выкладывается на
оба канала, строго в таком порядке:

1. **Новый сервер.** Установщик, затем манифест с
   `url = https://update.elitesip.vip:8081/releases/EliteSIP-0.1.56.exe`.
   Проверка: манифест 200 и подпись сходится с ключом клиента, установщик
   200/206, sha256 и размер совпадают, без пары — 401. После этого выпуск виден
   и в Spark: тот читает тот же `releases/current.json`.
2. **Только после этого — R2.** Тот же установщик байт в байт и второй
   манифест, подписанный тем же ключом, но с `url` на `get.elitesip.vip`. Это
   последняя запись в R2.
3. **Дальше — только новый сервер.**

Почему старые машины не отправить качать с нового сервера: клиент ≤ 0.1.55
шлёт пару Basic на любой хост из `url`, и полагаться на это нельзя.

Порядок 1 → 2 обязателен: наоборот машины обновились бы до 0.1.56 и пошли на
новый сервер раньше, чем там появился манифест.

### Чего не получат машины, оставшиеся на 0.1.55

- Правок предустановок и отзывов из Spark: те пишутся только на новый сервер.
- Активации новым ключом: пакета нет в R2. **Новые рабочие места ставить сразу
  с 0.1.56.**

## Как выпускать (с 0.1.57 и дальше)

Один раз на машине сборки, вне репозитория, в `%APPDATA%\EliteSIP-release\`:

- `provisioning.json` — заводская настройка выпуска: `updates.baseURL`,
  `user`, `password`, `presetsPublicKey`, `releasesPublicKey`;
- `publish.local.json` — доступы к каналам (заполняет владелец, в чат и
  журналы не выводится):

```json
{
  "update": {
    "baseURL": "https://update.elitesip.vip:8081",
    "basicAuth": "elitesip:…",
    "adminToken": "…"
  },
  "legacy": {
    "baseURL": "https://get.elitesip.vip",
    "basicAuth": "elitesip:…",
    "r2": { "accountId": "…", "bucket": "elitesip-updates", "accessKeyId": "…", "secretAccessKey": "…" }
  }
}
```

Пару можно задать одной строкой `basicAuth` или двумя полями `basicUser` и `basicPassword`; `baseURL` понимается в любом регистре.

`adminToken` — переменная CI `ELITESIP_ADMIN_TOKEN` в GitLab-проекте
`elitesip_update`. Раздел `legacy` после 0.1.56 не нужен.

Дальше:

```powershell
.\tools\release.ps1 -Version 0.1.57 -SigningKey C:\keys\releases.key -SkipSigning -Notes "…"
.\tools\publish.ps1 -Channel update -Version 0.1.57
```

`release.ps1` собирает и прогоняет проверки, кладёт заводскую настройку в
публикацию (отказывается, если её `baseURL` не совпадает с `-BaseUrl` или в ней
есть `releasesURL`), собирает установщик, сверяет `.pub` рядом с ключом с
`releasesPublicKey` настройки, подписывает манифест и читает его кодом клиента.
`publish.ps1` сверяет манифест с установщиком ещё до сети (версия, `url` на
этом же канале, sha256, размер), кладёт сначала установщик, потом манифест, и
проверяет канал: манифест байт в байт и его подпись, установщик по sha256 и
размеру, `Range`, 401 без пары. `-VerifyOnly` — только проверка.

Установщик собирается без подписи Authenticode (сертификата нет, см.
`RELEASE-SIGNING.md`): SmartScreen может предупредить при ручной установке.

Режим `publish.ps1 -Channel legacy` устарел. Удалить его, когда все машины
будут на 0.1.56+ (видно в Spark по отметкам `seen/`).

Переходный выпуск собирался так:

```powershell
.\tools\release.ps1 -Version 0.1.56 -SigningKey … -SkipSigning -LegacyBaseUrl https://get.elitesip.vip
.\tools\publish.ps1 -Channel update -Version 0.1.56
.\tools\publish.ps1 -Channel legacy -Version 0.1.56   # только после успеха предыдущей
```

## Пилот перед выкладкой (с 0.1.67)

Канал один, и выпуск расходится по всем включённым машинам за несколько часов:
приложение спрашивает канал раз в два часа, обновляльщик ставит в течение
десяти минут после согласия. Разные тайминги машин — это не пилот: посмотреть
на первые машины и остановить остальные никто не успевает.

Поэтому между `release.ps1` и `publish.ps1` — день:

1. `release.ps1` собрал установщик в `artifacts\`.
2. Администратор ставит его руками на 3–5 рабочих мест разных типов: офис и
   удалённое, гарнитура и колонки, Windows 10 и 11.
3. Смена на этих местах. Смотреть: `%LOCALAPPDATA%\EliteSIP\crash.log` пуст,
   регистрация держится, звонки слышны в обе стороны.
4. Только после этого — `publish.ps1`.

## Аварийный путь (с 0.1.67)

Если выпуск всё-таки роняет приложение на запуске, обычное обновление
невозможно: согласие на исправление даёт приложение, а оно не работает.
Обновляльщик это распознаёт и ставит исправление сам:

- приложение, прожив минуту, пишет `%ProgramData%\EliteSIP\started` с версией;
- обновляльщик запоминает, когда впервые увидел установленный выпуск
  (`{app}\updates\installed-seen`);
- если для установленного выпуска отметки о запуске нет дольше часа и
  приложение не запущено ни в одном сеансе — следующий выпуск с канала
  ставится без согласия (по-прежнему только подписанный и только новее).
  В `{app}\updates\updater.log` это видно строкой «АВАРИЙНАЯ установка».

Значит, лечится сломанный выпуск так: собрать исправление с версией выше,
выложить — машины поднимутся сами в пределах часа и одного такта задачи.
Откатить на прежний номер нельзя по-прежнему: исправление — всегда новая
версия.

Путь работает только с машинами, где уже стоит 0.1.67 или новее: у прежних
выпусков нет ни отметки о запуске, ни этой логики в обновляльщике.

## Метки выпусков (с 0.1.67)

`publish.ps1` ставит метку `v<версия>` на текущий коммит, если дерево чистое
и версия в `Directory.Build.props` совпадает с выкладываемой; иначе подсказывает
команду. На сервер метка отправляется руками: `git push origin v<версия>`.

## После выкладки

- Машина на 0.1.55 видит 0.1.56 и ставит его; после установки все запросы идут
  на `update.elitesip.vip:8081`; предустановка и `access/<id>` читаются,
  повторная активация не понадобилась.
- Чистая установка 0.1.56 активируется свежим ключом из Spark.

Проверка «манифест разобрался» этого не заменяет: установщик запускает
Windows, а не мы.

## Рантайм .NET (с 0.1.60)

С 0.1.60 выпуск зависит от рантайма: .NET Desktop Runtime 10 стоит на машине
отдельно, в `C:\Program Files\dotnet` (путь разрешён SRP). Выпуск — около 50
файлов и 30 МБ вместо 316 файлов и 173 МБ.

Установщик сам проверяет рантайм до любых изменений на машине. Нет — скачивает
его с `aka.ms/dotnet/10.0/windowsdesktop-runtime-win-x64.exe` и ставит тихо.
Не встал — установка отменяется, прежняя версия остаётся рабочей. Поэтому
машине, которую обновляют с 0.1.59 и раньше, нужен выход в интернет к
серверам Microsoft; при подготовке машины без сети рантайм ставится заранее
тем же установщиком Microsoft.

При обновлении с самодостаточных выпусков установщик удаляет из каталога
программы старые библиотеки рантайма: найдя `hostfxr.dll` рядом с exe,
запускатель .NET взял бы рантайм оттуда, и программа бы не стартовала.
