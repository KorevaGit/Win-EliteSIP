# Изменения Windows для переноса на macOS и Linux

Дата: 22 октября 2026. Эталон поведения — Windows **0.1.82**, метка `v0.1.82` в `KorevaGit/Win-EliteSIP`.

Документ охватывает изменения выпусков 0.1.80–0.1.82: завершение звонка из очереди при автоподъёме, форму главного окна, его заголовок, перенос карточки входящего, стандартный рингтон и сигнал подключения. Другие ОС в рамках выпуска 0.1.82 не изменялись.

## 2. Завершение входящего при автоподъёме

### Причина

В Windows `PhoneService.Offer` выходил из ветки автоподъёма до запуска `FollowIncomingAsync`. SIP-агент обрабатывал завершение, но приложение не снимало линию, медиасессию и открытую запись истории. Повторный отбой уже не находил SIP-звонка. Пользователь подтвердил включённый автоподъём в проблемном случае.

### Требуемый порядок

1. Создать запись звонка и подписаться на его события **до любой ветки автоподъёма**.
2. Для `Ended`, `Failed` и закрытия потока событий выполнять завершение истории и освобождение линии, аудиосессии, сокетов и порта.
3. Сериализовать запуск входящего медиа и его очистку. Если BYE пришёл, пока запускался звук после 200 OK, очистка должна дождаться запуска и снять его результат. Запуск не должен создать линию после уже выполненной очистки.
4. Сброс до ответа не должен оставлять окно или рингтон; сброс после ответа не должен оставлять занятое устройство и зависшую кнопку отбоя.

Windows: `src/EliteSIP.App/Shell/PhoneService.cs`: `Offer`, `AnswerAsync`, `AnswerIncomingCoreAsync`, `FollowIncomingAsync`, `_incomingMedia`.

Linux: тот же набор методов находится в `shared/src/EliteSIP.App.Core/Shell/PhoneService.cs`. Исправление уже перенесено коммитом `7420234`.

macOS: в проверенном `EliteSIP/App/AppModel.swift` подписка `callTasks[call.callID]` создаётся до `settings.autoAnswer.answers`. В запуске медиа уже проверяется существование линии после ожидания устройства; исчезнувшая линия приводит к освобождению сессии. Эту защиту сохранить и проверить сценариями ниже.

## 3. Главное окно: размер и размещение

- Исходная ширина — **324 логические точки**, минимальная ширина — **270**.
- При отсутствии сохранённого размера высота рассчитывается по пропорции **4:3**, то есть при ширине 324 получается **432**.
- Формула: `min(max(round(width * 4 / 3), contentMinimumHeight), workAreaHeight)`.
- Если содержимому требуется больше 432, окно берёт необходимую высоту в пределах рабочей области монитора. Не срезать кнопку звонка/отбоя и макросы.
- Если оператор уже изменял размер вручную, восстанавливается его размер. Обновление не сбрасывает пользовательский размер к стандартному.
- Окно должно оставаться в пределах своего монитора после изменения DPI, размера или состава экранов. Сохраняется существующее поведение нижней кромки при росте содержимого.

Это логические размеры окна WPF с рамкой, а не физические пиксели экрана. При переносе на другую ОС учитывать её масштаб и рамку, сохраняя пропорцию и доступность содержимого.

Windows: `Panel/PanelWindow.xaml.cs`, `PhoneAspect`, `InitialHeight`, `RestoreSize`, `UpdateMinimumHeight`.

Linux: поведение уже есть в `src/EliteSIP.App.Linux/Panel/PanelWindow.axaml.cs`, включая `PhoneAspect = 4.0 / 3.0`. Не заменять его фиксированной высотой для всех мониторов.

## 4. Полоса заголовка

Заголовок визуально согласован с фоном и текстом клиента и меняется вместе со светлой/тёмной темой. Кнопки сворачивания, разворачивания и закрытия сохраняют принятый на платформе вид и поведение.

Windows: `Theme/SystemCaption.cs`:

- Сохраняются штатные кнопки и рамка.
- На Windows 11 используются точные цвета DWM: атрибуты 35 (`CaptionColor`) и 36 (`CaptionTextColor`). Фон берётся из `window.Background`, текст — из `TextPrimaryBrush`.
- Windows 10 этих атрибутов не поддерживает: применяется существующий светлый/тёмный режим системной полосы через 20/19. Произвольный точный цвет на Windows 10 данным изменением не реализован.
- Изменение применяется при показе и при смене темы уже открытых окон.

Linux: `Program.cs` уже включает собственную рамку Avalonia, а `Theme/Palette.axaml` содержит `TitleBarBackgroundBrush` для обеих тем. Сохранить эту реализацию, проверив вид, смену темы и стандартные действия кнопок.

Для macOS перенести требуемое визуальное поведение с учётом её собственных оконных кнопок; Windows-атрибуты DWM туда не относятся.

## 5. Карточка входящего: перенос и сохранение

### Общие правила

1. Карточку можно перенести мышью за шапку. Перенос не принимает и не отклоняет вызов, не забирает клавиатурный фокус из CRM и не меняет правила проверки кнопки «Ответить».
2. При включённой защите и случайной позиции каждый новый вызов продолжает появляться случайно. Перенос текущего окна не выключает рандомизацию и не перезаписывает сохранённую фиксированную позицию.
3. Для следующего случайного смещения предыдущей считается фактическая последняя позиция окна, включая перенос оператором.
4. При выключенной случайной позиции или всей защите используется последнее место, выбранное оператором. Оно сохраняется сразу после окончания переноса и переживает звонки и перезапуск.
5. Если сохранённой позиции ещё нет, карточка появляется по центру рабочей области экрана курсора.
6. Сохранённая позиция восстанавливается на своём мониторе, даже если курсор уже на другом. Если монитор исчез, выбирается ближайший доступный и окно возвращается внутрь его рабочей области.
7. После переноса на другой монитор учитываются его рабочая область, DPI и отступы политики. Во время самого переноса окно не нужно возвращать на исходный монитор.
8. Автоматическое размещение и закрытие окна позицию не сохраняют. Завершение вызова во время переноса не должно сохранять уже закрытую карточку.

### Размер карточки и реализация Windows

- Ширина — **320 логических точек**. Высота определяется содержимым (`SizeToContent="Height"`), фиксированной высоты нет.
- `WindowChrome.CaptionHeight = 28`: невидимая область переноса над шапкой. Кнопки приёма остаются в клиентской области.
- `WM_ENTERSIZEMOVE`/`WM_EXITSIZEMOVE` отличают перенос оператором от программного размещения. На окончании переноса поднимается `MovedByUser`.
- Запрет активации `WS_EX_NOACTIVATE` и ответ `MA_NOACTIVATE` сохраняются.
- `IncomingCallPresenter` предоставляет `RestorePlacement` и `SavePlacement`; приложение связывает их с настройками.
- Позиция хранится атомарным значением **`incomingPlacement.origin`**, с `x`/`y` в физических пикселях Windows. Она отдельна от политики защиты, учётной записи и управляемых полей Spark.
- Новый раздел включён в `AppSettings.AutoSave`. Старые файлы без него читаются с пустой позицией. При переносе на другую ОС не копировать физические координаты Windows в её логические точки без преобразования.
- Границы рабочей области округляются внутрь до целых пикселей: иначе при масштабе 125% отступ 10 точек превращается в 12,5 пикселя и округление `SetWindowPos` может вывести край окна за допустимую область.

Файлы Windows: `Incoming/IncomingCallPresenter.cs`, `Incoming/IncomingCallWindow.xaml[.cs]`, `Settings/IncomingWindowPlacementSettings.cs`, `Settings/AppSettings.cs`, связка в `App.xaml.cs`.

Linux: переносить в платформенное окно `src/EliteSIP.App.Linux/Incoming/` и соответствующий общий presenter/настройки, сохраняя `IIncomingCallView` и `IUiThread`. macOS: исходные точки — `EliteSIP/Windows/IncomingCallPanel.swift` и настройки приложения; перенос за фон уже включён, требуется проверить сохранение и правила рандомизации.

Подробный отдельный контракт: [INCOMING-WINDOW-PLACEMENT.md](INCOMING-WINDOW-PLACEMENT.md).

## 6. Стандартный рингтон

Пользователь выбрал **вариант 1 из второй подборки — мягкий двойной телефонный звонок**. В Windows установлен именно прослушанный WAV без изменения звучания.

| Параметр | Значение |
|---|---|
| Эталонный ресурс | `src/EliteSIP.App/Assets/ringtone.wav` |
| Формат | WAV PCM, 16 бит, моно, 48 000 Гц |
| Длительность | 12 секунд: три одинаковых цикла по 4 секунды |
| Рисунок | Два мягких звонка, затем пауза |
| SHA-256 | `2CCD7DF4586A25CC42298944BEC6FA9AA7FB3B548167396AB0E78C7D9E3E5535` |

Ресурс синтезирован без внешних семплов. Генератор: `tools/sound-design/generate_telephone.py`; требуется Python с NumPy. Результат варианта 1 — `artifacts/sound-proposals/telephone-v2/01-soft-double-bell.wav`. При переносе предпочтительно взять эталонный WAV из Git и сверить SHA-256.

Не менять выбранный оператором собственный файл и сохранённую громкость. Порядок источников остаётся: собственный читаемый файл → стандартный WAV → существующий аварийный синтез, если файл отсутствует/не читается. Рингтон повторяется до ответа, отклонения или отмены; предпрослушивание в настройках использует тот же источник и настройки вывода.

Windows кладёт ресурс рядом с программой как `ringtone.wav`. Linux-проект уже включает `shared/src/EliteSIP.App/Assets/ringtone.wav` в публикацию — при переносе обновить ресурс в общей ветке и указатель подмодуля. На macOS заменить стандартный ресурс бандла, используемый `EliteSIP/Services/Ringtone.swift`, сохранив выбор собственного файла и устройства.

## 7. Сигнал подключения к разговору

- Короткий мягкий сигнал **340 мс**, тише существующего отбоя примерно на 7 дБ по пиковому уровню.
- Две перекрывающиеся ноты вверх: 523,25 и 659,25 Гц; вторая начинается через 110 мс. Плавные атака и спад, без щелчков.
- Работает для входящего ручного ответа, автоподъёма и исходящего звонка после успешного запуска медиа и назначения активной линии.
- Звучит **один раз** для первого подключения данного звонка. Не играть на гудках/ранних медиа, удержании, повторном ответе, смене линии или уже завершившемся вызове.
- Сигнал локальный, на настроенном устройстве разговора оператора; не подмешивать его в RTP. Звук не должен останавливать рингтон, гудки другой линии или аудио разговора.
- Отказ проигрывания подсказки не должен завершать звонок или ронять приложение.

Windows: `SignalSoundPlayer.PlayConnected` и `ConnectedToneProvider` в `src/EliteSIP.Audio/SignalSoundPlayer.cs`. Вызов находится в `PhoneService.MarkAnswered`: проверяются первый ответ, состояние SIP `Answered` и совпадение с `ActiveCallId`.

Синтез: моно, 48 кГц, общий множитель 0,032. Для точного переноса использовать реализацию `ConnectedToneProvider`; эквивалент для генерации WAV находится в `connection()` файла `tools/sound-design/generate.py`. Пик эталона около −29,94 dBFS. Изменение частоты дискретизации на платформе не должно менять длительность, высоту нот и относительную громкость.

Linux использует интерфейс `ISignalSounds` из `shared/src/EliteSIP.Audio/SignalSounds.cs` и вывод через `src/EliteSIP.Audio.Pulse/PulseSignalOutput.cs`. Потребуется добавить операцию подключения в общий интерфейс/проигрыватель и вызвать её в `shared/src/EliteSIP.App.Core/Shell/PhoneService.cs` после тех же проверок. Одного копирования WAV рингтона для этого недостаточно.

На macOS соответствующее место — `EliteSIP/Services/CallSounds.swift`; вызов связать с успешным подключением активной линии в `AppModel.swift`. Сохранить отдельное локальное проигрывание на выбранном устройстве разговора.

## 8. Приёмка на каждой платформе

Проверить следующие сценарии на реальной машине после автоматических проверок:

| Сценарий | Ожидаемый результат |
|---|---|
| Очередь, автоподъём, клиент сбросил до/во время ответа | Нет зависшего окна, линии, аудиоустройства или открытой истории |
| Отбой одновременно с запуском медиа | После завершения запуска всё освобождено, линия не появляется заново |
| Новый профиль без сохранённого размера главного окна | Вытянутая форма 4:3, содержимое и нижние кнопки видимы |
| Ранее выбранный оператором размер | Восстановлен, не сброшен обновлением |
| Светлая/тёмная тема, смена темы на живом окне | Заголовок согласован с клиентом; кнопки окна действуют штатно |
| Перенос входящего при рандомизации | Текущий вызов переносится; следующий снова случайный; фиксированное место не переписано |
| Перенос без рандомизации → новый вызов → перезапуск | Последнее место восстановлено |
| Два монитора, разные DPI, отключение одного | Карточка остаётся видимой; восстановление выбирает подходящий монитор |
| Сброс вызова во время переноса | Окно закрыто, позднее окончание переноса не сохраняет его |
| Стандартный/собственный рингтон и предпрослушивание | Новый стандартный звонок слышен; собственный файл и громкость сохранены |
| Входящий, автоподъём и исходящий после подключения | Один тихий сигнал на устройстве разговора |
| Гудки, удержание, повторный ответ, отказ и быстрый сброс | Ложного сигнала подключения нет |

Регрессионные тесты Windows: `IncomingLifecycleTests` (6 сценариев автоподъёма), `IncomingPlacementTests` (7 сценариев размещения), `ConnectionToneTests` (длительность, уровень, конечность потока и плавность). Геометрия и защита дополнительно покрываются пакетами `CallGuard` и существующими проверками разметки.

## 9. Порядок переноса и выпуска

1. Получить Windows `v0.1.82` и этот документ. Проверить текущее состояние целевой ветки, чтобы не перезаписать уже внесённые правки.
2. Перенести недостающие изменения с учётом платформенных интерфейсов и координат. Для Linux общий код менять в Windows-репозитории, коммитить и публиковать там; в Linux-репозитории менять свои виды/вывод и указатель `shared`.
3. Проверить новый ресурс по SHA-256, сохранение настроек и сигналы на выбранных устройствах.
4. Выполнить автоматические проверки и сценарии приёмки выше на macOS/Linux, включая реальный звонок через АТС.
5. Собрать и подписать выпуск собственной линии платформы. Для Linux использовать его отдельный ключ, собственную версию и `releases/linux/`; не использовать ключ Windows.
6. После публикации проверить скачанный манифест, его подпись клиентским кодом, SHA-256/размер пакета, доступ к установщику и реальное обновление одного рабочего места.
